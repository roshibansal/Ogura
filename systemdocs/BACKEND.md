# 30 — Backend Architecture

## 30.1 What "backend" is here [CONFIRMED]

There is **no dedicated application server**. The backend is composed of three layers, all owned by Supabase (project `yudzgkrjsstqbfrrrrly`, `supabase/config.toml:1`):

1. **Postgres + PostgREST** — the browser talks directly to Postgres tables through the auto-generated PostgREST API via `@supabase/supabase-js` (`src/integrations/supabase/client.ts`). All authorization for this path is enforced by **Row-Level Security (RLS) policies**, not by any server code. [CONFIRMED, /tmp/extract/db.txt "=== POLICIES ===", "=== RLS ENABLED ==="]
2. **Deno Edge Functions** (`supabase/functions/**`) — 14 serverless HTTP handlers used for anything that needs a secret, an external API call, elevated (service-role) DB access, or AI/webhook orchestration. [OBSERVED, `ls supabase/functions`]
3. **Database functions/triggers** (`pg_proc`, `public` schema) — `handle_new_user`, `handle_seller_approval`, `has_role`, `cleanup_expired_otps`, `update_updated_at_column`. These execute business rules and role grants *inside Postgres*, invoked by `AFTER INSERT` on `auth.users`, `AFTER UPDATE` on `sellers`, and `BEFORE UPDATE` triggers respectively. [CONFIRMED, psql `pg_proc` dump]

There is no Node/Express/Nest server, no queue worker, no cron service, and no container running app logic outside Deno edge functions. [CONFIRMED — absence verified via `files.txt`/repo listing: only `supabase/functions/**` and static Vite frontend]

## 30.3 The MCP server function [CONFIRMED]

`supabase/functions/mcp/index.ts` is **auto-generated** (banner: "AUTO-GENERATED by @lovable.dev/mcp-js — do not edit") from source in `src/lib/mcp/**` (`src/lib/mcp/index.ts`, `src/lib/mcp/supabase.ts`, `src/lib/mcp/tools/*.ts`), bundled by the Lovable Vite plugin. It is deployed as a normal Supabase edge function named `mcp`.

- Exposes an MCP (Model Context Protocol) server (`defineMcp`) named `ogura-mcp` with three tools: `search_products`, `get_product`, `list_my_orders` (`supabase/functions/mcp/index.ts:70-149`).
- Auth: OAuth issuer mode — `auth.oauth.issuer({ issuer: "https://yudzgkrjsstqbfrrrrly.supabase.co/auth/v1", acceptedAudiences: "authenticated" })` (`mcp/index.ts:158-161`). This makes the MCP endpoint itself a **Supabase Auth OAuth resource server**: callers must present a bearer token validated against Supabase Auth's `/auth/v1` issuer to be treated as authenticated (`ctx.isAuthenticated()` / `ctx.getUserId()`), but two of the three tools work unauthenticated using the anon key (`supabaseOptionalUser`).
- DB access inside MCP tools uses the **publishable/anon key**, forwarding the caller's bearer token as `Authorization` header (`supabaseForUser`, `mcp/index.ts:57-64`) — i.e. it rides on RLS, not service role. [CONFIRMED]
- `list_my_orders` requires authentication and is scoped to `customer_id = ctx.getUserId()` (`mcp/index.ts:131-140`), consistent with the `orders` RLS policy "Customers can view own orders".

## 30.6 Service-role usage points [CONFIRMED]

Service-role key (`SUPABASE_SERVICE_ROLE_KEY`, bypasses RLS) is read via `Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')` in:
- `supabase/functions/razorpay-verify-payment/index.ts` — inserts the `orders` row after payment verification, bypassing the `orders` INSERT RLS policy check (`auth.uid() = customer_id`) because it runs as service role, trusting `order_data.customer_id` from the request body instead. [SECURITY-SENSITIVE — HIGH: any caller can pass an arbitrary `customer_id`/`seller_id` in `order_data` and, if they can also forge a valid Razorpay signature (they cannot, since `RAZORPAY_KEY_SECRET` is server-side) — but see 36 for the more realistic partial-failure risk.]
- `supabase/functions/send-otp/index.ts` — reads/writes `otp_verifications` as service role (table has no public RLS policy allowing anon insert otherwise, since it's not listed under RLS-enabled table policies for anon).
- `supabase/functions/verify-otp/index.ts` — same, plus uses `supabase.auth.admin.listUsers()` and `supabase.auth.admin.generateLink()` (Auth Admin API — full auth control) to look up/create sessions for phone-based logins.

No other edge functions instantiate a service-role client; all others use only external HTTP APIs or no DB access. [CONFIRMED by grep of edge function bodies]

## 30.7 Transaction boundaries [OBSERVED / MISSING]

- Postgres itself provides single-statement atomicity for each individual insert/update (default Supabase behavior). [CONFIRMED]
- There is **no multi-statement transaction** anywhere in the edge functions. The clearest example: `razorpay-verify-payment` performs a single `orders` insert but the corresponding `order_items` insert is done **separately from the browser** after this function returns (see `Checkout.tsx` — actually `order_items` insertion is not shown to happen at all in the reviewed code path; only `orders` is inserted server-side). This means order header and line items are not created atomically, and if the order insert fails, payment has already succeeded. [SECURITY-SENSITIVE / MISSING — see `36_ERROR_HANDLING.md`]
- No use of `supabase.rpc()` wrapping multiple writes in a single Postgres function/transaction was found. [MISSING]

## 30.8 Idempotency [MISSING except where noted]

- `send-otp`: idempotent-ish by construction — deletes prior unverified OTPs for the phone before inserting a new one, and rate-limits re-send to 60s (`send-otp/index.ts:33-52`). [CONFIRMED]
- `razorpay-create-order`: **not idempotent** — no idempotency key sent to Razorpay; a caller invoking twice creates two separate Razorpay orders. [MISSING]
- `razorpay-verify-payment`: **not idempotent** — no check for whether an order with this `razorpay_payment_id`/`tracking_id` already exists before inserting; a retried client call (e.g. browser reload after `handler` fires) could insert a duplicate `orders` row for the same payment. [MISSING, SECURITY-SENSITIVE — MEDIUM: duplicate order records, no unique constraint on `tracking_id`]
- `sync-algolia`: re-syncs full catalog each invocation; safe to re-run (upsert-style) but not confirmed transactional. [INFERRED]
- Edge functions in general have no `Idempotency-Key` header handling. [MISSING]

## razorpay-verify-payment
- File: `supabase/functions/razorpay-verify-payment/index.ts` (173 lines). verify_jwt=false.
- Purpose: verify Razorpay HMAC signature and, on success, insert the `orders` row using the service-role client.
- Invocation: `src/pages/Checkout.tsx:208`, inside the Razorpay `handler` callback (client-side, after payment popup completes).
- Input: `{ razorpay_order_id, razorpay_payment_id, razorpay_signature, order_data }`. `order_data` is **entirely client-constructed** (see Checkout.tsx:172-195): `customer_id`, `seller_id` (fallback to `customer_id` if absent — `index.ts:~100`), `subtotal`, `shipping_fee`, `discount`, `total`, `shipping_address`, `items[]`.
- Signature check: HMAC-SHA256 over `${orderId}|${paymentId}` using `RAZORPAY_KEY_SECRET`, constant computed and string-compared (`verifySignature`, lines 9-31) — **not constant-time comparison** [SECURITY-SENSITIVE — LOW: timing side channel, low practical exploitability over network].
- Env: `RAZORPAY_KEY_SECRET=REDACTED`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY=REDACTED`.
- DB writes: `orders` insert only (service role, bypasses RLS) with `order_number = 'OGR' + base36(Date.now())`, `status:'new'`, `tracking_id: razorpay_payment_id`. **No `order_items` insert happens in this function** — `order_data.items` is accepted in the payload but not written anywhere found in this file [MISSING — order line items are apparently never persisted server-side by this flow; see `33_BUSINESS_LOGIC.md`].
- Response: success case `{ success:true, payment_verified:true, order_saved:true/false, order_number, payment_id, ... }`; on `orderError` it still returns **HTTP 200 with `success:true, order_saved:false`** — i.e. payment success is reported to the client even when the DB write failed (`index.ts:~118-132`) — partial-state risk documented in `36_ERROR_HANDLING.md`.
- Security: [SECURITY-SENSITIVE — HIGH] `customer_id`, `total`, `subtotal`, pricing entirely trusted from client input with a service-role insert; nothing cross-checks `total` against the Razorpay-captured `amount`, nor `customer_id` against the authenticated caller (function is unauthenticated and never calls `supabase.auth.getUser()`). A user who can produce a valid Razorpay signature for *any* amount they actually paid could set `customer_id` to another user's UUID or fabricate `total`/`discount` values for the stored order record. Financial/data-integrity risk.

## verify-otp
- File: `supabase/functions/verify-otp/index.ts` (249 lines). verify_jwt: not in config.toml [UNKNOWN].
- Purpose: verify OTP and sign the user in (creating a Supabase Auth session) via a synthetic email `${phone}@ogura.phone.auth`.
- Input: `{ phone, otp, name? }`; OTP must match `/^\d{6}$/`.
- Logic: fetch latest OTP row for phone → reject if none/expired (deletes expired record) → reject if `attempts>=5` (deletes record) → recompute SHA-256(`otp+phone`) and compare to stored hash → on mismatch increments `attempts` and returns 401 → on match, looks up existing auth user by scanning **all** users via `auth.admin.listUsers()` and matching `email === phoneEmail` [SECURITY/PERF-SENSITIVE — MEDIUM: `listUsers()` is O(all users) per verification, not scoped/filtered — will not scale and is a needless full-table admin scan] → if found, generates a magic-link token (`auth.admin.generateLink`) and immediately exchanges it (`auth.verifyOtp`) to mint a session; if not found, [truncated in review — creates the user, per standard pattern, not fully re-confirmed line-by-line beyond line ~150].
- DB: reads/writes `otp_verifications` (marks `verified:true` only after a session is actually established — "wait until user creation/login succeeds", a good practice), updates `profiles.name/phone` for existing users.
- Env: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY=REDACTED`.

### RULE-SELLER-APPROVAL — Seller approval grants `seller` role
- DESCRIPTION: When an admin flips a seller's `application_status` to `approved`, a DB trigger grants that user the `seller` app role.
- TRIGGER: `UPDATE` on `public.sellers` row.
- ACTOR: admin (via `AdminApprovals`/`AdminSellers` UI, which must have `has_role(admin)` per `sellers` RLS "Admins can manage all sellers").
- PRECONDITIONS: row exists in `sellers`; caller passes `has_role(auth.uid(),'admin')` RLS check to perform the UPDATE.
- LOGIC (`handle_seller_approval`, AFTER UPDATE trigger, `pg_proc`): `IF NEW.application_status='approved' AND OLD.application_status!='approved' THEN INSERT INTO user_roles(user_id,role) VALUES (NEW.user_id,'seller') ON CONFLICT (user_id,role) DO NOTHING;`
- DATA READ: `OLD`/`NEW` row of `sellers`.
- DATA WRITTEN: `user_roles` insert (idempotent via `ON CONFLICT DO NOTHING`).
- STATE CHANGE: `sellers.application_status: pending|rejected → approved` triggers `user_roles += {user_id, 'seller'}`.
- SUCCESS: role granted exactly once even if approved multiple times (conflict-safe).
- FAILURE: none observed — trigger has no error branch; if insert somehow fails, whole UPDATE transaction rolls back (trigger runs in same transaction).
- EXCEPTION: transitioning **from** `approved` back to `pending`/`rejected` does **not** revoke the `seller` role — no corresponding "downgrade" trigger exists. [MISSING/GAP — see 34]
- SECURITY REQUIREMENT: only reachable if caller holds `admin` role (enforced by DB RLS on the `sellers` UPDATE, not by app code) — DB-enforced, not client-trust-based. [CONFIRMED, strong]
- SOURCE FILE: DB trigger only (no direct edge-function/app-code equivalent found).
- DATABASE SOURCE: `pg_proc.handle_seller_approval`; `sellers_application_status_check` CHECK constraint restricts values to `pending|approved|rejected`.
- RELATED UI: `src/pages/admin/AdminSellers.tsx` (approvals), `AdminApprovals.tsx`.
- RELATED FLOW: seller onboarding.
- CONFIDENCE: CONFIRMED.

# 35 — Background Jobs / Async & Scheduled Processing

There is **no scheduler** (no `pg_cron`, no Supabase Scheduled Function config found in `supabase/config.toml`, no external cron referenced in code). [CONFIRMED — absence]. All "background-ish" behavior in this system is either (a) a DB trigger that fires synchronously inside another transaction, or (b) long-polling/SSE done entirely within the lifetime of a single HTTP request from an edge function. There are no durable queues, no retry workers, and no job table.

## Implemented "background" mechanisms

### JOB-OTP-CLEANUP — `cleanup_expired_otps` trigger
- TRIGGER: fires as a **DB trigger**, not a schedule — attached to `otp_verifications` (per `pg_proc`, function body is `DELETE FROM otp_verifications WHERE expires_at < now(); RETURN NEW;`); given the `RETURN NEW` pattern it is a `BEFORE`/`AFTER` trigger on INSERT (most likely `BEFORE INSERT ON otp_verifications`, consistent with "clean up old rows every time a new OTP is requested" — not independently confirmed which trigger event fires it, but it is bound to table activity, not a clock). [CONFIRMED function body; INFERRED exact trigger-event binding]
- SCHEDULE: none — purely reactive to new OTP inserts (i.e., only runs when `send-otp` is called). If nobody requests an OTP, expired rows accumulate indefinitely.
- FUNCTION: `public.cleanup_expired_otps()`.
- INPUT: none (uses `now()`).
- PROCESS: single `DELETE ... WHERE expires_at < now()`.
- DB READ: `otp_verifications.expires_at`.
- DB WRITE: `DELETE` on `otp_verifications`.
- EXTERNAL CALL: none.
- SUCCESS/FAILURE: implicit — runs inside the same transaction as the triggering INSERT; if it fails, the whole INSERT fails (fails closed).
- RETRY: none needed (deterministic idempotent delete).
- IDEMPOTENCY: yes (delete-by-condition, safe to re-run).
- TIMEOUT: none (bounded by table size at trigger time — could be slow if the table grows very large, but no expected large volume given OTPs self-limit via manual delete on verify failure too).
- LOCKING: standard row locks for the DELETE, no explicit lock/advisory-lock usage.
- DUPLICATION RISK: none.

### JOB-VIRTUAL-TRYON-POLL — long-poll/SSE inside `virtual-tryon` edge function
- TRIGGER: single HTTP invocation from `useVirtualTryOn.ts:137`.
- SCHEDULE: none — synchronous within the request; "polling" is actually the client hook re-invoking the function (client-side setInterval/retry logic in `useVirtualTryOn.ts`, not independently re-verified line-by-line) when the response comes back `{loading:true}`.
- FUNCTION: `supabase/functions/virtual-tryon/index.ts`.
- PROCESS: joins a Gradio SSE queue, reads events for up to `MAX_WAIT_MS=90_000`ms, then returns whatever state it reached (done, still-loading, or error).
- EXTERNAL CALL: Hugging Face Space (`yisol-idm-vton.hf.space`), bearer-token authenticated.
- SUCCESS: base64 image returned to client; client then does its own `tryon_history` insert.
- FAILURE: various soft-fail (`loading:true`) vs hard-fail (`error` string) outcomes as detailed in 33/31.
- RETRY: delegated entirely to the client hook re-calling the function — no server-side retry or backoff logic, no server-side job record, so if the client gives up (closes tab), the Gradio Space job (if still running remotely) has no cleanup/cancellation call made.
- IDEMPOTENCY: each invocation creates a *new* Gradio `session_hash` — retries are not deduplicated against a possibly-still-running prior job, so a user hitting "try again" repeatedly could stack multiple concurrent generations against the same HF quota.
- TIMEOUT: hard 90s abort via `AbortController`.
- LOCKING/DUPLICATION RISK: no request coalescing — concurrent/duplicate try-on requests for the same image pair are not detected or merged, driving unnecessary cost against the (secret-gated but unauthenticated-endpoint) HF token.

### JOB-SOCIAL-WEBHOOK-RELAY — synchronous outbound webhook
- TRIGGER: single HTTP call from `socialPostService.ts:82` → `social-post-webhook` edge function → single `fetch(MAKE_WEBHOOK_URL, ...)`.
- SCHEDULE: none, fully synchronous request/response.
- RETRY: none — a single failed `fetch` to Make.com surfaces as a 502 to the browser (`{success:false,error,status}`) with no server-side retry/backoff/dead-letter queue.
- IDEMPOTENCY: none — a client retry after a timeout could double-post to the same Make.com scenario.
- DUPLICATION RISK: real — no idempotency key is generated or checked.

### JOB-ALGOLIA-SYNC — full catalog re-index (trigger source unconfirmed)
- TRIGGER: `sync-algolia` edge function — **no scheduled invocation found in this repo** (no cron entry, no `pg_cron` job, no client call site). Likely triggered manually via the Supabase dashboard, an external cron outside this repo, or ad hoc by a developer. [MISSING/UNKNOWN — the *mechanism* that keeps Algolia in sync with `products` changes over time could not be located]
- PROCESS: reads all products (service role, bypassing RLS — filter completeness not independently confirmed, see 33 RULE-PRODUCT-VISIBILITY) plus hardcoded demo data, upserts into Algolia index `ogura-products`.
- IDEMPOTENCY: `saveObjects`-style upsert is generally idempotent by Algolia `objectID`, but re-running does not *remove* Algolia objects for products that were deleted/hidden since the last sync unless the function explicitly diffs and deletes stale objects (not confirmed — file too large to fully audit in this pass). [UNKNOWN — potential for orphaned/stale search results if products are deleted or set non-live between syncs, i.e. **index/sync drift is a real, unmitigated risk** given there is no trigger-on-product-change and no confirmed schedule]
- DUPLICATION/DRIFT RISK: HIGH — because nothing triggers this automatically on product create/update/delete, the Algolia index can silently diverge from `products` for an unbounded period.

## 36.1 Frontend validation failures

- DB STATE: no write attempted.
- RECOVERY: user corrects and resubmits. No logging beyond browser console in most cases.

## 36.2 Edge function errors (general pattern across all 14 functions)
- Every function wraps its body in `try{...}catch(error){ console.error(...); return new Response(JSON.stringify({success:false/error:...}), {status:500, headers: corsHeaders}) }` (`31_EDGE_FUNCTIONS.md`). Logging is `console.error` only, visible in Supabase function logs, not surfaced to any external monitoring/alerting system found in this repo. [CONFIRMED pattern, MISSING: no Sentry/error-tracking integration found]
- CORS headers are attached even to error responses, so failures are visible to the calling browser as structured JSON rather than opaque CORS failures — good practice, but no `Retry-After` header or standardized error code taxonomy is used anywhere.

## 36.3 DB errors (RLS denial, constraint violation)
- TRIGGER: client attempts a write blocked by RLS (e.g. seller tries to update another seller's product; anon tries to insert into `orders`).
- ERROR SURFACED: PostgREST returns `42501` (insufficient_privilege, effectively "0 rows affected" for RLS on UPDATE, or an explicit error on INSERT `with_check` failure) or `23514`/`23505` for CHECK/UNIQUE violations (e.g. `products_status_check`, `orders_status_check`). Supabase JS client surfaces this as `{data:null, error:{code,message,details,hint}}`.
- OBSERVED RUNTIME EXAMPLE [CONFIRMED, `/tmp/extract/runtime.txt`]: navigating to `/product/x` (non-UUID id) causes `ProductDetail.tsx` to query `.eq('id','x')` against a `uuid` column → Postgres error `22P02 invalid input syntax for type uuid: "x"` surfaced as an HTTP 400 from PostgREST, logged in the browser console as `[PDP] DB error: {code: 22P02, details: null, hint: null, message: "invalid input syntax for type uuid: \"x\""}`. RESULTING UX: page renders "Product not found" heading (graceful fallback) rather than a crash — [CONFIRMED via runtime capture]. Similarly `/store/x` renders "Brand store not found" for the equivalent brand-store lookup. This is correct defensive handling of a malformed-ID case, but note the *underlying* 400 is a genuine DB-level type error, not an intentional "not found" query — i.e. any bot/crawler/user typing a non-UUID slug generates a logged error server-side (Postgres/PostgREST access logs) even though the user experience is clean. [SOURCE: `src/pages/ProductDetail.tsx` (query near line 67), runtime capture]
- RECOVERY: none needed beyond the graceful UI fallback; no retry, no user-facing distinction between "truly not found" and "malformed id causing a DB type error."

## 36.4 Network failures
- TRIGGER: `supabase.functions.invoke()` or `.from().select()` calls fail due to connectivity loss.
- ERROR SURFACED: generic thrown error caught by the calling component's `try/catch`, typically a `toast({title:"Error", variant:"destructive"})`.
- SPECIFIC EXAMPLE — Checkout: `Checkout.tsx:267-273` catches any error from the payment flow (order-create call, verify call, or Razorpay SDK itself) and shows `"Payment Error — Something went wrong. Please try again."`, resetting `isProcessing`. If the failure happens *after* Razorpay's `handler` already fired (i.e. payment succeeded) but the `verify-payment` invocation itself network-fails (not just a business-logic failure inside it), the catch block at `Checkout.tsx:236-243` shows `"Payment verification failed. Please contact support."` — **the cart is NOT cleared and NOT navigated away in this branch** (`clearCart()`/`navigate()` only happen inside the try's success path, `Checkout.tsx:225-234`), so the user is left on the checkout page having already paid, with their cart still full, likely to attempt paying again. [SECURITY/UX-SENSITIVE — HIGH, CONFIRMED by code reading `Checkout.tsx:205-243`] — this is the clearest "double-charge" risk surface in the app: a network hiccup exactly at the verify-payment call boundary can lead a paying customer to retry checkout for an already-charged amount, with no order-lookup-by-payment-id safety net anywhere in the code to detect "you already paid for this."

- TRIGGER B — user cancels the Razorpay modal: `options.modal.ondismiss` (`Checkout.tsx:253-260`) resets `isProcessing`, shows "Payment Cancelled... Your cart is still saved." Clean, correctly reversible, no DB writes involved.
- TRIGGER C — **order insert fails after payment succeeds** [PARTIAL/INCONSISTENT STATE — CONFIRMED, HIGH SEVERITY]: `razorpay-verify-payment/index.ts:112-127`. Sequence: HMAC signature is valid (real payment happened) → `supabase.from('orders').insert(...)` fails (e.g. transient DB error, a NOT NULL violation on a field the client omitted such as `shipping_address`, or an FK violation if `order_data.customer_id` doesn't correspond to a real user) → function returns **HTTP 200** with `{success:true, payment_verified:true, order_saved:false, error:'Order save failed, please contact support'}`. On the client, `Checkout.tsx:220` checks `verifyError || !verifyResponse?.success` — since `success:true` here, **this branch is NOT treated as an error by the client**: `clearCart()` runs and the user is navigated to `/order-confirmation` with an `orderNumber` of `undefined` (`verifyResponse.order_number` is not set when `order_saved:false`, since `savedOrder` stays `null`) and a `paymentId` that IS valid. RESULT: **the customer sees an apparent success/confirmation screen with a missing order number, their cart is cleared, they believe the order is placed, but no `orders` row exists in the database at all** — a fully invisible order for both the seller and any admin/support lookup keyed by order number, recoverable only if support can search by the raw Razorpay `payment_id` manually. [CONFIRMED via code read of `Checkout.tsx:220-234` + `razorpay-verify-payment/index.ts:112-127` — this is the single most severe error-handling defect found in the system]
- TRIGGER D — **order_items insert fails after orders insert succeeds** [PARTIAL/INCONSISTENT STATE — CONFIRMED, HIGH SEVERITY]: `razorpay-verify-payment/index.ts:143-150`. The `orders` row is already committed (`savedOrder` set) by this point. If the `order_items` insert then fails (e.g. a `product_id` FK violation, or `quantity<=0` check violation, or any transient error), the code only does `console.error('Failed to save order items:', itemsError)` — **no error is added to the client-facing response at all**; the function still returns `order_saved:true` (since `savedOrder` is truthy) with a full `order_number`. RESULT: an `orders` header row exists with **zero line items**, and the customer/seller/admin sees a "successful" order with no products attached — a data-integrity defect that is completely silent to every party except whoever reads the edge function's server logs. [CONFIRMED via code read, `razorpay-verify-payment/index.ts:143-150`]
- No compensating transaction, no retry queue, and no reconciliation job exists for either TRIGGER C or D (cross-ref `35_BACKGROUND_JOBS.md` "Payment reconciliation" MISSING entry) — once the response is sent, this system has no further mechanism to detect or repair the inconsistency.
- Not idempotent: a client-side retry of `razorpay-verify-payment` (e.g. user refreshes after seeing a hung "Processing..." state) with the same valid signature would pass verification again and **insert a second, duplicate `orders` row** (no unique constraint on `tracking_id`/`razorpay_payment_id`), compounding the risk. [CONFIRMED — no such constraint in `db.txt "=== CONSTRAINTS ==="`]

## 36.7 AI / storage failures
- AI gateway (`ai-recommendations`, `image-analysis`, `generate-banner-image`): 429 (rate limit)/402 (payment required, i.e. Lovable AI credits exhausted) passthrough from `ai.gateway.lovable.dev`; malformed model JSON is regex-salvaged, else falls back to `[]`/error object — no retry/backoff implemented, single attempt only. USER EXPERIENCE: recommendation carousels silently show nothing (`useRecommendations` empty state) rather than an error banner — a fail-soft design choice appropriate for a non-critical feature.
- Storage upload failures (`supabase.storage.from(...).upload(...)` in `SellerAddProduct.tsx`, `DashboardAddProduct.tsx`, `SellerApply.tsx`, `useVirtualTryOn.ts`): errors are checked (`const {error} = await ...upload(...)`) and presumably surfaced via toast in each caller (pattern consistent with the rest of the codebase, not individually re-verified per file in this pass). If an upload succeeds but the subsequent `products`/`sellers`/`tryon_history` insert referencing that URL fails, the uploaded file becomes an orphan (cross-ref `35_BACKGROUND_JOBS.md` orphan-asset MISSING entry) — no cleanup/rollback of the storage object occurs.

## 36.8 Timeouts
- `virtual-tryon`: hard 90s `AbortController` timeout → treated as a soft "still loading" state, not a hard failure, pushing retry responsibility to the client hook (see 35).
- No other edge function sets an explicit timeout; Deno/Supabase platform default function timeout (not configured in this repo, platform default applies) would be the effective ceiling for `sync-algolia` (749 lines, potentially large full-catalog operation) and `image-analysis` (two sequential AI calls) — risk of the platform terminating these mid-operation with no partial-progress handling. [INFERRED risk, platform default timeout not verified in this repo]

## 36.9 Rate limits
- `send-otp`: explicit 60-second app-level rate limit per phone (429). No rate limiting exists on any other function — `razorpay-create-order`, `ai-recommendations`, `image-analysis`, `virtual-tryon`, `social-post-webhook`, `sync-algolia` are all unauthenticated and uncapped, relying solely on the upstream provider's own rate limiting (Razorpay, Lovable AI Gateway, Hugging Face, Make.com) to eventually reject abusive volume — the abuse is felt as *cost/quota exhaustion* to the OGURA operator, not blocked at OGURA's own edge. [SECURITY-SENSITIVE — MEDIUM/HIGH depending on function, cross-ref `30/31`]

## 36.10 Duplicate requests
- Covered specifically for payments in 36.6 (Trigger C/D context) — the general pattern across the whole edge-function set is: **no function anywhere implements an `Idempotency-Key` header or a dedupe check against a natural key** (`razorpay_payment_id`, `phone`+OTP window, waitlist submission phone/email, etc.), so double-submits (double-clicks, browser back-button resubmission, retried fetches after a timeout) can create duplicate DB rows in `orders`, `brand_waitlist_applications`, `seller_applications`, and `otp_verifications` (mitigated there specifically by the delete-before-insert pattern in `send-otp`, the one exception).

## 36.11 Stale state
- Cart prices are captured at add-to-cart time (client memory) and never re-validated against current `products.price` at checkout (cross-ref 33 RULE-CHECKOUT-TOTAL) — if a seller changes a price between add-to-cart and payment, the customer pays the stale price with no reconciliation.
- Applied discount codes are validated once at "Apply" time; if the code's `usage_limit`/`end_date`/`status` changes between application and actual payment completion (arbitrary time gap while the user fills in address/payment), the stale discount amount is still sent to `razorpay-verify-payment` and persisted unchecked.
- `sellers.is_active`/`is_verified` staleness: a product's continued "live" visibility does not appear to re-check the owning seller's current `is_active`/`application_status` at read time (RLS "Anyone can view live products" only checks `products.status`/`is_available`, not any join to `sellers`) — **a deactivated or de-approved seller's previously-live products may remain publicly visible and purchasable** unless a separate cleanup step (not found) demotes their `products.status`. [SECURITY/BUSINESS-SENSITIVE — MEDIUM, INFERRED from absence of a cross-table check in the RLS policy text]

## 36.12 Deleted product / account
- `products.designer_id`/`vendor_id` use `ON DELETE CASCADE` (deleting a designer/vendor deletes their products) — but `products.seller_id` has **no observed FK constraint listed** in the reviewed constraint dump (only `designer_id`/`vendor_id` FKs appear under `products` in `db.txt "=== CONSTRAINTS ==="`) — meaning a seller row could be deleted (e.g. via `sellers_user_id_fkey ... ON DELETE CASCADE` when the underlying `auth.users` row is deleted) while `products.seller_id` still points to the now-gone seller, producing orphaned products with a dangling `seller_id`. [SECURITY-SENSITIVE — MEDIUM, CONFIRMED absence of an FK on `products.seller_id` in the reviewed constraint list; INFERRED consequence]
- Deleting an `auth.users` row cascades to `sellers` (`sellers_user_id_fkey ... ON DELETE CASCADE`) but **`profiles` has no FK relationship confirmed in this pass** to `auth.users` for cascade behavior — [UNKNOWN, not independently verified] — and `orders.customer_id`/`order_items` have no FK listed either in the reviewed excerpt, so a deleted customer account could leave `orders` rows with a dangling `customer_id`, permanently orphaning seller-side order history for that customer with no referential-integrity error raised (since no FK exists to enforce it). [INFERRED from absence in constraint dump — should be independently re-confirmed with a direct `\d+ orders` before treating as certain]

## Summary: flows that can leave partial/inconsistent DB state
1. **`razorpay-verify-payment` — `orders` insert fails after payment succeeds** (`index.ts:112-127`; client treats as success, `Checkout.tsx:220-234`) — money charged, no order record, customer sees a broken confirmation screen. HIGH severity, no recovery path except manual support lookup by Razorpay payment ID.
2. **`razorpay-verify-payment` — `order_items` insert fails after `orders` insert succeeds** (`index.ts:143-150`) — order exists with zero line items, completely silent failure (server log only). HIGH severity.
3. **Network failure exactly at the verify-payment call boundary** (`Checkout.tsx:205-243`) — payment succeeded at Razorpay, verify call itself network-fails, cart is retained and user is invited to "contact support" with no reference number surfaced, and no safeguard preventing them from paying again for the same cart. HIGH severity, real double-charge risk.
4. **Non-idempotent payment verification** — duplicate `orders` rows possible on client retry (no unique constraint on `tracking_id`). MEDIUM-HIGH severity.
5. **Orphaned storage uploads** when a subsequent table insert fails after a successful file upload (product images, try-on images). LOW-MEDIUM severity (cost/hygiene, not correctness).
6. **Dangling `products.seller_id`/possibly `orders.customer_id`** on account/seller deletion, absent confirmed FKs. MEDIUM severity, needs direct schema re-confirmation.

All six trace to the same root cause identified throughout this document set: **no multi-statement transactions and no reconciliation job exist anywhere in this system** (cross-ref `30_BACKEND_ARCHITECTURE.md §30.7-30.8`, `35_BACKGROUND_JOBS.md` "Payment reconciliation" MISSING entry).
